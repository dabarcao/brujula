- (note) Why: production app Brujula has no boundary between GUI and backend -- 25 files call Supabase directly today. User wants that separated so interface changes never risk backend/anonymity logic and vice versa; also wants a seam to eventually remove Supabase for direct Postgres. Combination of a pain (tight coupling blocking safe iteration) and a vision (own API-key-secured core). Distilled from finalized architecture spine at _bmad-output/planning-artifacts/architecture/architecture-brujula-gui-2026-09-11/ARCHITECTURE-SPINE.md.
- (capability) CAP-1 intent: the GUI (pages and client components) reads and writes all Brujula data exclusively through a managers/API boundary, never Supabase directly. success: an ESLint no-restricted-imports rule reports 0 violations of @/lib/supabase/* or @/server/db/* under src/app/** and src/components/**, enforced in CI or pre-commit.
- (capability) CAP-2 intent: each of the six existing domains (report groups, admin/members, cycles, feedback, responder/invitation, read-only reports) exposes its business logic through one manager, reachable both in-process (Server Components/Actions) and over HTTP (Route Handlers for Client Components and future clients). success: for each migrated domain, the same manager function is demonstrably invoked from both an in-process caller and a Route Handler with identical results.
- (capability) CAP-3 intent: the API layer authenticates the GUI via an app-owned token, decoupled from (issued alongside, not replacing) the Supabase session, while RLS keeps enforcing authorization underneath during the transition. success: a request to app/api/** without a valid app token is rejected (401) even carrying a valid Supabase session cookie; existing RLS-backed operations continue passing their current authorization behavior unchanged.
- (capability) CAP-4 intent: anonymous invitee flows (responder/invitacion, single-use token) keep working exactly as today, authenticated by their existing token rather than the new app token. success: an invitee can view and submit a response end to end with no login and no app token present.
- (capability) CAP-5 intent: each domain migrates to the new layering behind a feature flag with a safe rollback path, validated by a minimum automated safety net before the flag flips. success: each migrated domain ships behind USE_NEW_API_<DOMAIN> (default off), has 2-3 passing Vitest integration tests (auth-boundary, anonymity-threshold, golden-output) against a locally seeded DB, and the old code path is removed only after one full production cycle on the new path.
- (constraint) Zero automated test coverage and no CI/staging exist today -- bends CAP-5 toward a local-seeded-Vitest tripwire plus per-domain feature flags rather than a full test suite or CI-gated rollout.
- (constraint) Postgres RLS (23 policies, 9 migrations) is the sole live authorization mechanism, keyed off Supabase auth.uid() inside SECURITY DEFINER RPCs -- bends CAP-3 to issue the new app token ALONGSIDE the Supabase session rather than replacing it, since db/* must still hold a real Supabase session for RLS to keep working.
- (constraint) ~35 existing Postgres RPCs already carry business logic and are battle-tested (two prior RLS-recursion bugs already fixed) -- bends CAP-1/CAP-2 to wrap RPCs as-is inside the DB-access layer rather than port their logic into TypeScript.
- (constraint) This is a live production app serving real customer organizations, with the team's established discipline of small sequential changes (66 migrations to date) -- bends CAP-5 to a strict risk-ascending, one-domain-at-a-time rollout rather than a batched cutover.
- (non_goal) Replacing RLS with application-level authorization checks is explicitly out of scope for this spec -- deferred to a future initiative, done only once Supabase itself is actually scheduled for removal.
- (non_goal) Actually swapping the DB-access layer's Supabase client for direct Postgres access is out of scope -- this spec only builds the seam (CAP-1's db/ isolation) that makes that swap contained later.
- (non_goal) Introducing CI or a staging environment is out of scope for this spec -- open question, revisit before the report-groups POC (first CAP-5 slice) is considered done.
- (non_goal) The Brujula Segura visual redesign (DESIGN.md/EXPERIENCE.md, new UI tokens/components) is a separate, parallel initiative with its own spec -- out of scope here beyond the data-fetching pattern note that Client Components call the new API via a shared fetch wrapper.
- (note) Success signal: all six domains run on the new managers/API layering with their feature flags removed (old direct-Supabase paths deleted), the ESLint boundary rule holds at 0 violations repo-wide, and the report-groups POC slice (first delivered) demonstrably works end to end -- create, respond, close, AI interpretation -- against seeded demo data with its flag on before any other domain starts.
