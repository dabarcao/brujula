- (constraint) [ADOPTED] Brownfield production app, zero automated tests, no CI, no staging environment, 66 sequential single-purpose SQL migrations as the team's established discipline.
- (constraint) [ADOPTED] Current state: 25 files call Supabase directly (6 Server Action files under src/app/actions/, 19 Server Component pages). ~35 Postgres RPCs already encapsulate business logic DB-side. RLS (23 policies, 9 migrations) is the sole live authorization mechanism, keyed off Supabase auth.uid(). No service-role key used anywhere.
- (decision) [ADOPTED] Design paradigm: layered architecture, three layers under new src/server/ tree: db (data access) -> managers (business logic/orchestration) -> API (GUI-facing boundary). Goal: GUI never touches Supabase/Postgres directly.
- (decision) [ADOPTED] src/server/db/*.ts (one file per domain: cycles, feedback, reportGroups, members, admin, responder) is the ONLY layer permitted to import a Supabase/Postgres client. Existing ~35 RPCs stay as-is and count as part of this layer (RLS-scoped, battle-tested) -- their logic is not ported into TypeScript. This is the deliberate seam for a future Supabase-to-direct-Postgres swap.
- (decision) [ADOPTED] src/server/managers/*.ts (cyclesManager, feedbackManager, reportGroupsManager, membersManager, adminManager, authManager, aiInterpretationManager) call db/* only, own orchestration/business logic, never call Supabase directly, contain no redirect()/revalidatePath(). aiInterpretationManager moves near-verbatim from src/lib/aiInterpretation.ts as the reference example.
- (constraint) [ADOPTED] Enforcement mechanism: ESLint no-restricted-imports rule -- only src/server/managers/* may import a Supabase client; src/app/** and src/components/** are forbidden from importing @/lib/supabase/* at all. This, not the HTTP boundary, is what actually prevents drift.
- (decision) [ADOPTED] Managers layer exposed two ways: (1) in-process TypeScript calls from Server Components and Server Actions (kept as 'use server' form-action wrappers, now one-line delegates) -- no self-fetch round trip, same serverless function boundary, only latency cost; (2) real HTTP src/app/api/**/route.ts Route Handlers for Client Components (ResponderWizard, ScaleSlider, CompetencyPicker, EvaluatorPicker, EmailEvaluatorPicker, CompetencyComparisonChart, CompetencyRadar) and future non-browser clients, paired with src/lib/api/client.ts fetch wrapper (same-origin, local useState loading/error, no state-management library).
- (decision) [ADOPTED] Auth/token: the app builds its OWN API-key/token scheme for the API layer -- explicit user decision, rejected reusing the Supabase session cookie, because Supabase itself is a planned future removal (moving to direct Postgres). Route Handlers authenticate via a new requireApiToken(), not the Supabase cookie session.
- (assumption) [ASSUMPTION] Token mechanism: own first-party session token issued at login, stored as a separate httpOnly+Secure+SameSite=Lax cookie (not Authorization-header bearer in browser storage), mirroring the security properties of the Supabase cookie it replaces and avoiding XSS-exposed token storage. Token issuance/rotation/expiry lifecycle is implementation detail for the scaffolding epic, not fixed here.
- (decision) [ADOPTED] Transition safety: the db/ layer keeps authenticating to Supabase/Postgres under the hood during the transition so RLS continues enforcing authorization as a safety net WHILE the new token scheme changes how the GUI proves identity to the API. Full RLS-to-application-code authorization rewrite is an explicit separate future epic, done only once Supabase is actually being removed -- not bundled into this pass.
- (constraint) [ADOPTED] Known discrepancy to verify early: src/lib/supabase/server.ts has a comment claiming session refresh is handled by 'the middleware', but no middleware.ts exists anywhere in the repo. Flag and check during first implementation slice (report-groups POC).
- (decision) [ADOPTED] New shared UI primitives live in src/components/ui/ -- pure presentation, no data/manager/Supabase imports -- kept strictly separate from src/lib/api/ (fetch wrapper) and src/server/managers/.
- (decision) [ADOPTED] Rollout sequencing, domain migration order (risk-ascending, smallest/most-isolated first): 1) report groups (POC) 2) admin/members + auth 3) cycles 4) feedback (anonymity-critical) 5) responder/invitation (external anonymous critical path -- last) 6) read-only reports (dashboard, mi-mapa, informe-empresa). Per-domain UI redesign follows that domain's backend migration, not before.
- (decision) [ADOPTED] Minimum viable safety net: install Vitest, run against a local supabase-start instance seeded via existing scripts/seed-*.mjs (never production). 2-3 integration tests per migrated domain: auth-boundary rejection, anonymity-threshold enforcement, golden-output check for cycle-closing/report generation (old path vs new path, same seed, identical output).
- (decision) [ADOPTED] Rollback/deploy safety given no staging/CI: dual-path coexistence per domain behind a simple env flag (e.g. USE_NEW_API_CYCLES, default off), manual QA against seeded scratch DB before each flip, one domain/one flag/one deploy at a time (never batched), delete old path only after new path survives one full production cycle.
- (decision) [ADOPTED] Sequencing of the two initiatives: global/additive redesign work (design tokens, fonts, palette, shared chrome) can start anytime in parallel; per-domain UI redesign (radar animation, trust/anonymity UI) is sequenced after that domain's backend migration epic.
- (assumption) [ASSUMPTION] Error response envelope for src/app/api/**/route.ts: JSON body { error: { code: string, message: string } } with appropriate HTTP status code (401/403 auth, 404 not found, 422 validation, 500 unexpected) -- not specified in the brief, adopted as a sane convention since two independently-built route handlers could otherwise diverge on error shape.

- (decision) [FIX, rubric-walker CRITICAL] AD-5/AD-6 reconciliation: the new requireApiToken() is a GUI-facing identity check only. db/* still obtains its Supabase client using the user's real Supabase session (set at the same login that issues the new app token), because existing RPCs are SECURITY DEFINER and hand-check auth.uid() (confirmed supabase/schema-dump.sql get_responder_context, submit_feedback_response). - (decision) [FIX, adversarial CRITICAL] feedback_requests shared-table ownership: cyclesManager and feedbackManager both read the feedback_requests table (discriminated by request_type per docs/spec.md and supabase/migrations/0001_initial_schema.sql) via db/cycles.ts and db/feedback.ts respectively, but ownership of WRITE/lifecycle operations follows the existing RPC naming split already in Postgres: cyclesManager calls only cycle-specific lifecycle RPCs (create_feedback_cycle, close_cycle_request, organize_cycle_evaluators); feedbackManager calls only ad-hoc-specific lifecycle RPCs (create_ad_hoc_feedback_request*, close_ad_hoc_feedback_request). Neither manager re-implements or duplicates the other's lifecycle RPC call. A shared read-only helper (e.g. request status/type lookup used by both) lives once in whichever db file needs it first and the other imports it -- never duplicated.
