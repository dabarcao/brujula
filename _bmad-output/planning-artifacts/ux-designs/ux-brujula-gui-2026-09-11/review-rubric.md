# Spine Pair Review — brujula-gui UX

## Overall verdict

The pair is structurally sound: section order matches the required BMad shape exactly in both files, every `{components.*}` and `{colors.*}` reference spot-checked resolves to a real frontmatter token, and the two Key Flows are genuinely excellent — named protagonist, numbered steps, an explicit climax beat, a failure path. But two categories fail on substance rather than mechanics: measured WCAG contrast on the coral and amber role/reveal treatments is below AA at the sizes the mocks actually use, directly contradicting the Accessibility Floor's own claim; and the brainstorm's specific trait-transfer grafts (9+ named product borrowings) are almost entirely absent from the spine's reasoning, with only 2 of them actually carried through. A downstream implementer could build from this today, but would ship an inaccessible reveal button/role badge and lose the "why" behind most of the brainstorm's screen-specific borrowing decisions.

## 1. Flow coverage — adequate

Both Key Flows (Marta / Diego) have a named protagonist, numbered steps (6 each), an explicit **Climax beat:** callout, and a stated failure path. No misses on the mechanical checklist for the two flows that exist.

### Findings
- **Moderate** Only 2 Key Flows exist against ~14 named IA surfaces, and zero flow covers the Supervisor/HR-facing register (Informe empresa, Admin, Ciclos management, Grupos creation) — even though DESIGN.md and EXPERIENCE.md both treat that register as structurally distinct (denser grid, Leapsome-style density, the aggregate-chrome badge). (EXPERIENCE.md "Key Flows" §75-105 vs. "Information Architecture" §16-33.) Fix: add a third flow for a Supervisor/HR persona (e.g., reviewing Informe empresa, or creating a cycle) so the aggregate-chrome pattern gets exercised end-to-end, not just described in isolation.
- **Minor** Login/Registro and Invitación (accept/decline) are named IA surfaces with no flow, and no State Patterns entry either (see Finding under §4). Fix: at minimum give Invitación a one-paragraph mini-flow or fold its accept/decline states into State Patterns.

## 2. Token completeness — thin

Color-token bookkeeping is strong: 24 light tokens, 24 matching `-dark` tokens, all valid hex, no missing pairs (verified by diffing frontmatter key lists). All `{colors.*}`/`{components.*}`/`{rounded.*}`/`{spacing.*}`/`{typography.*}` references in both files' prose resolve to a defined frontmatter key — zero broken references found. Where it breaks down is the actual AA math on load-bearing color combinations, which the task specifically asked to spot-check.

### Findings
- **Critical** White text on `{colors.coral}` (#FF6B4A) measures **2.82:1**, below both the 4.5:1 normal-text and 3:1 large-text AA thresholds. This is the reveal-button's label color (DESIGN.md `components.reveal-button`, §102-106) and EXPERIENCE.md's own Accessibility Floor asserts this combination "clears WCAG AA at body size... large-scale button label" (EXPERIENCE.md §70) — that claim is false at the size actually specified: `mockups/key-report-reveal.html` renders the label at 14px/weight 600, which doesn't even qualify as WCAG "large text" (needs ~18.66px bold or 24px regular), and the ratio fails the large-text floor anyway. Fix: darken coral for this specific fill-with-text use (a `coral-deep`-on-white-text pairing, or a genuinely large/bold label), and correct the Accessibility Floor claim.
- **Critical** White text on `{colors.role-coach}` (#C98A2E) measures **2.93:1** — same failure, on the role-badge pill for the Coach role (DESIGN.md `components.role-badge`, §122-124). The role-badge component entry never specifies a text color at all — it has `radius` and `fontFamily` but no `color` field — so this failure had nothing to be checked against in the token contract itself. Fix: add an explicit `color` (or per-role text-color rule) to `components.role-badge` and re-verify all 5 role fills against it — role-catalizador shares coral's 2.82:1 failure.
- **Major** `{colors.coral-deep}` text on `{colors.coral-wash}` (bookmark-chip) measures **3.93:1**, below the 4.5:1 normal-text AA floor (the chip label is 14px per the mock, not WCAG-large). Fix: darken coral-deep slightly or lighten coral-wash further.
- **Minor** The typography scale asserted in prose ("display 32/40, h1 26/32, h2 20/26, body 16/26, caption 13/18," DESIGN.md §169) is never promoted into frontmatter `fontSize`/`lineHeight` fields the way `typography.body` and `typography.caption` already are — `typography.display` and `typography.heading` have no `fontSize` token at all, so an implementer must mine prose for half the scale. Fix: add `fontSize`/`lineHeight` to the `display`/`heading` frontmatter entries to match `body`/`caption`.
- Not a finding, but note: `{colors.ink-soft}` and `{colors.ink-soft-dark}` are defined and clearly implied (secondary/meta text throughout the mocks) but never actually referenced via `{colors.ink-soft}` bracket syntax anywhere in either file's prose — harmless, but slightly inconsistent with how the rest of the palette is cited.

## 3. Component coverage — adequate

All 11 `components.*` frontmatter entries (button-primary, button-secondary, reveal-button, card, card-accent, anonymity-badge, role-badge, saboteador-bar, intensity-scale, progress-bar, bookmark-chip) have a matching behavioral rule in EXPERIENCE.md's Component Patterns / Interaction Primitives / State Patterns. 10 of the 11 also have a prose bullet in DESIGN.md's `## Components` section.

### Findings
- **Major** `ScaleSlider` (EXPERIENCE.md "Interaction Primitives," §65 — "the existing `ScaleSlider` component... this redesign only restyles its track/thumb to the new token set") is a named, actively-restyled UI component with **no DESIGN.md entry whatsoever** — not in frontmatter `components`, not in the `## Components` prose section. Its only visual spec ("indigo fill, `{rounded.full}` thumb") lives inline in EXPERIENCE.md, inverting the doc pair's own stated division of labor (DESIGN.md owns visuals, EXPERIENCE.md owns behavior). Fix: add a `components.scale-slider` frontmatter row and a `## Components` bullet in DESIGN.md; trim the inline visual detail out of EXPERIENCE.md once it has a real home.
- **Moderate** The aggregate-view badge ("Vista agregada — [N] personas," EXPERIENCE.md "Aggregate-chrome distinction," §46; rendered as `.agg-badge` in `mockups/key-dashboard-home.html`) has no component token at all — only a bare `{colors.surface-2}` color citation, no radius, no typography, unlike every other chip/badge in the system (anonymity-badge, role-badge, bookmark-chip all have full frontmatter rows). Fix: give it a `components.aggregate-badge` entry.
- **Minor** `{components.button-secondary}` is defined in frontmatter (DESIGN.md §97-101) and used correctly in EXPERIENCE.md, but has no bullet in DESIGN.md's `## Components` prose section (§189-200) the way every other component does — asymmetric documentation, not a broken reference.

## 4. State coverage — thin

Loading, threshold-not-met (the anonymity-threshold empty state), generic error, saved/paused, and revealed-vs-not-revealed are all named, correctly scoped to non-red/non-error tones per the "no red/green" rule, and tie cleanly to the two Key Flows.

### Findings
- **Major** **Permission-denied is never addressed anywhere in State Patterns**, despite Informe empresa and Admin being explicitly Supervisor-only / platform-admin-only surfaces (EXPERIENCE.md "Information Architecture" §24, §26; DESIGN.md's own "Do's and Don'ts" §208 discusses aggregate screens at length). What a non-Supervisor or non-admin sees when they land on these routes is entirely undefined — a real gap for a product with role-gated aggregate views, not a hypothetical one. Fix: add a permission-denied row to State Patterns (plain-language, same register as the generic Error state, no red).
- **Moderate** Dashboard home has no empty state — every mock and every prose description (EXPERIENCE.md IA §19; `mockups/key-dashboard-home.html`) shows the populated "Tienes 2 ciclos abiertos" case only. A brand-new user or a lull between cycles has no specified treatment. Fix: add an empty-dashboard row to State Patterns.
- **Minor** Mi mapa (the employee's own aggregated competency map) has no first-time/no-closed-cycles-yet empty state, distinct from the per-request threshold-not-met state already covered — a new hire with zero closed 360s hits an unspecified page.

## 5. Visual reference coverage — adequate

All three mocks are linked inside EXPERIENCE.md at accurate, correctly-captioned locations, verified against the actual mock HTML: `key-dashboard-home.html` at the IA "Dashboard home" bullet (§19) and again in the Component Patterns intro blockquote with an accurate "card-accent vs. aggregate-chrome contrast" caption (§41) — matches the mock's actual `.card-accent` grid + `.agg-badge` contrast. `key-report-reveal.html` at Key Flow 1 (§79) and in the same intro blockquote, captioned "collapsed + revealed states" — matches the mock's Estado 1/Estado 2 structure exactly. `key-wizard-question.html` at Key Flow 2 (§94) and the intro blockquote, captioned "wizard question + bookmark/paused states" — matches. No placement or caption inaccuracies found.

### Findings
- **Moderate** DESIGN.md itself contains **zero** mockup links — `grep -n "mockups/" DESIGN.md` returns nothing. The Colors and Components sections are the most purely visual sections in either document (the 5-role palette, card vs. card-accent, saboteador-bar softness) and would benefit most from a pointer into the mocks that actually render them; instead the mock↔spine relationship is entirely one-directional (EXPERIENCE.md → mocks only). Fix: add at least one "(see `mockups/key-report-reveal.html` for the role-color palette and saboteador-bar in context)"-style link in DESIGN.md's Colors or Components section.

## 6. Bloat & overspecification — strong

No findings worth flagging: prose stays tightly load-bearing throughout (each paragraph in Colors/Layout ties back to a spec.md section or a memlog decision rather than decorative color theory), the Do's and Don'ts section restates Colors/Components content as intended imperative pairs rather than new prose, and no pixel value duplicates a token that already exists. The one place raw pixels leak past the token system (the typography scale) is already logged under §2 rather than repeated here.

## 7. Inheritance discipline — adequate

### Findings
- Component names are identical, case-for-case, across both files everywhere checked (all 11 defined components; spot-checked `reveal-button`, `card-accent`, `saboteador-bar`, `intensity-scale`, `role-badge`, `bookmark-chip`, `progress-bar`, `anonymity-badge`, `button-secondary`). A full extraction of every `{...}` token reference in both files (grep, not sampling) confirms all resolve to a defined frontmatter key — zero broken references.
- **Moderate** `components.role-badge` (DESIGN.md §122-124) has no `color` field in its frontmatter — the exact property responsible for the two Critical contrast failures in §2. The inheritance chain (frontmatter → prose → EXPERIENCE.md behavior) is otherwise clean, but this one missing field is precisely why a real defect passed through undetected: there was no committed value to check.

## 8. Shape fit — thin

Section order in both files is complete and exactly matches the required order: DESIGN.md runs Brand & Style → Colors → Typography → Layout & Spacing → Elevation & Depth → Shapes → Components → Do's and Don'ts; EXPERIENCE.md runs Foundation → Information Architecture → Voice and Tone → Component Patterns → State Patterns → Interaction Primitives → Accessibility Floor → Key Flows. No section is out of place, none is missing from the required set.

### Findings
- **Major** "Inspiration & Anti-patterns" is omitted entirely, and per this review's brief that is a real gap here, not a stylistic omission. `brainstorm.html` (the 2026-09-11 source brainstorm) names at least 9 specific trait-transfer grafts, each tied to a specific screen: **Lattice → dashboard home** (card-accent "moments" treatment — carried through, DESIGN.md §194 / EXPERIENCE.md §19), **Leapsome → /admin & informe-empresa** (dense grid — carried through, DESIGN.md §175), **Duolingo → wizard-only micro-celebration** (implemented at EXPERIENCE.md §64, but never attributed to its source), and then six more that have **no trace at all** in either file: Culture Amp → soft illustration humanizing empty states (the actual Empty state spec, EXPERIENCE.md §56, is plain reassuring text with no illustration — this graft is not just unmentioned, it's contradicted by what was actually specified), 15Five → "Pedir feedback" framed as a light continuous habit rather than a formal event, BetterUp → a serene, generous-air, restrained-color treatment specific to the AI-narrative sections, Officevibe → playful nudges scoped only to low-risk invitations, Notion → minimal chrome/controlled line-width for mapa de competencias and informe de grupo, Linear → crisp, contained microinteractions for cycle-management screens, Airbnb → a verified-participation trust pattern in report headers, and GitHub → a persistent small participation-trend visual on Mi mapa. Only 2 of 9 survive into the spine's committed reasoning; the other 7 are neither implemented nor recorded as deliberately rejected — they're simply gone, which is exactly the provenance loss this section exists to prevent. Fix: add an "Inspiration & Anti-patterns" section to EXPERIENCE.md (or DESIGN.md, per the graft's nature) that either commits each remaining graft to a real spec location or explicitly records it as rejected, the way the Headspace/Notion "private reflection register" rejection is already captured in DESIGN.md's Brand & Style (§145).
