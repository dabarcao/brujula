01 · Architecture

What talks to what

02 · Application

How it's organized

The backend/GUI decoupling initiative (ARCHITECTURE-SPINE.md, AD-1 through AD-12) replaced "pages call Server Actions call Postgres RPC" with a strict three-layer stack. The ~35 existing Postgres RPCs didn't move — they're wrapped, not rewritten — but everything above them now goes through the same two TypeScript layers, whether the caller is a Server Component or a browser fetch().

The three layerssrc/server/**

src/ ├── app/ │ ├── api/ — 35 Route Handlers, the HTTP surface for Client Components │ │ └── api-docs/ — self-hosted Swagger UI at /api-docs │ ├── actions/ — 'use server' files: now thin one-line delegates to managers/* │ ├── admin/, dashboard/, login/, registro/ │ └── responder/[token]/, invitacion/[token]/ — token-only, no requireApiToken() ├── server/ │ ├── db/ — ONLY layer allowed to import a Supabase client (AD-1/AD-2), 8 files │ ├── managers/ — business logic + orchestration, calls db/* only, 8 files │ ├── infra/ — 3rd-party SDKs with no Supabase/RLS dimension (email.ts → Resend, AD-12) │ └── shared/ — auth.ts (app-token issue/verify), errors.ts ├── components/ — shared React components (radar, wizards, sliders…) └── lib/ ├── supabase/ — client.ts / server.ts, the only files db/* may import └── api/client.ts — browser-side fetch wrapper Client Components use to reach app/api/** proxy.ts — repo root; Next.js 16 renamed middleware.ts → proxy.ts, see §05 supabase/migrations/ — 0001…0096_*.sql, still the schema/RLS/RPC source of truth docs/ — spec.md, documento-funcional.md, feature-flags.md, this file
◇

The rule is enforced two ways, not just convention: an ESLint no-restricted-imports rule forbids src/app/**/src/components/** from importing @/lib/supabase/* or @/server/db/* directly, and every db/*/managers/*/infra/* file opens with import "server-only" — an accidental client-bundle import fails the build, not just lint.

API auth modelAD-5 / AD-6

  1. 01
    POST /api/auth/signin (email, password, x-brujula-csrf header) issues a new stateless, HMAC-signed brujula_app_token cookie alongside the unchanged Supabase session cookie — two separate credentials, not one replacing the other.
  2. 02
    Every other Route Handler gates on requireApiToken(): checks the app-token cookie's signature/expiry and, for mutating methods, the anti-CSRF header. It never reads the Supabase session — identity-to-API and identity-to-database are deliberately decoupled.
  3. 03
    Underneath, db/* still builds its Supabase client from the real Supabase session cookie, so existing RLS policies and SECURITY DEFINER RPCs stay the actual authorization backstop (AD-6) — the app token only proves "this request came from our own GUI," nothing about who the caller is.
  4. 04
    Full endpoint-by-endpoint request/response shapes: /api-docs (live, self-hosted, always in sync with the route code — this document intentionally doesn't duplicate that table).
◇

This dual-issuance is the planned Supabase-removal seam (AD-5): when Supabase Auth is eventually replaced, only the session-cookie half goes away — the app-token half and every Route Handler built against it are unaffected.

The two feedback flows

  1. 01
    Structured 360 cycle — a Supervisor creates a cycle (cyclesManager.createCycle) and selects participants. Each participant then organizes their own evaluators by category; self-evaluation is added automatically. organizeEvaluators/createIndividualRequest trigger the invitation emails themselves, from inside the manager, right after the RPC succeeds — so both the in-process (Server Action) and HTTP (Route Handler) call paths send mail identically.
  2. 02
    Ad-hoc / agile request — anyone requests feedback on a specific topic (meeting, collaboration, leadership initiative, general, competencias) from chosen colleagues or raw emails; one open request at a time, cancellable or editable until the first response lands.
△

The two flows aren't symmetric on email triggering. feedbackManager.createRequest/createIndividualRequest (ad-hoc) do not send invitation emails themselves — that trigger lives one layer up, in src/app/actions/feedback.ts's Server Action, a deliberate exception from when a parallel story had feedbackManager.ts locked. Calling the ad-hoc-request Route Handlers directly (bypassing the Server Action) creates the request but silently sends no mail. Worth normalizing into the manager if this domain gets touched again.

◇

Anonymity is still enforced at the Row-Level Security layer in Postgres, not by hiding a column in the UI — feedback_responses genuinely has no author field, and nothing about the new app-token/API layer changes that.

03 · Data

Database model

Schema still lives entirely as raw SQL — now 96 sequential files under supabase/migrations/, applied via the Supabase CLI (supabase db push), no ORM. The refactor didn't touch this layer's shape — it wraps the existing RPCs/RLS, it doesn't rewrite them — so the domain groupings below are unchanged from before, plus a few newer additions noted inline.

04 · Setup

Run it locally

Node 20+, the Supabase CLI, and a few minutes — supabase start now boots a full local Postgres + Auth + Studio stack and applies all 96 migrations for you. No more hand-pasting SQL one file at a time.

  1. 1
    Install dependencies: 
    npm install
  2. 2
    Start the local Supabase stack (Postgres, Auth, Studio) — applies every migration under supabase/migrations/ automatically: 
    npx supabase start
  3. 3
    Copy .env.example to .env.local. The CLI's fixed local URL/anon key are the defaults already in the example file; only APP_TOKEN_SECRET is required beyond that — generate a fresh one, never reuse it across environments: 
    NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=...          # supabase start prints this
APP_TOKEN_SECRET=...                        # node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
ANTHROPIC_API_KEY=...   # optional — narrative interpretation degrades to null without it
RESEND_API_KEY=...      # optional — email sending degrades to a silent no-op without it
NEXT_PUBLIC_SITE_URL=   # optional locally — only needed for links inside outgoing emails
  4. 4
    Start the dev server: 
    npm run dev
    The app is at http://localhost:3000, Supabase Studio at http://127.0.0.1:54323.
  5. 5
    Run the test suite (Vitest, scoped to db//managers//api/route.ts — no Server Component rendering tests, per AD-9): 
    npm test

05 · Production

Deployment

First real deployment happened after the refactor, not before — the pre-refactor version of this app never went to production. Hosted on Vercel (app) + Supabase (database/auth), both on their free tiers while usage is internal, per docs/spec.md.

Env varRequired?Vercel typeNotes
NEXT_PUBLIC_SUPABASE_URLYesConfigReal project URL, not the local CLI default.
NEXT_PUBLIC_SUPABASE_ANON_KEYYesConfigReal project anon key.
APP_TOKEN_SECRETYesSecretFresh value, never the same as local/test — requireApiToken() fails loud at request time if unset.
RESEND_API_KEYNoSecretUnset today in production — invitation/thank-you emails are a silent no-op until it's added. The sending domain (notificaciones@brujula.kairos-experience.es, hard-coded in infra/email.ts) must also be verified in Resend, independent of the key being valid.
ANTHROPIC_API_KEYNoSecretUnset today in production — AI narrative degrades to null, report still renders.
NEXT_PUBLIC_SITE_URLNoConfigFalls back to Vercel's own auto-populated VERCEL_URL, then localhost:3000. Only needed for a custom domain.

Gotchas found the hard way

△

middleware.ts silently doesn't work on Next.js 16 the way training data expects. The convention was renamed to proxy.ts/export function proxy(), and the default runtime changed from Edge to Node.js. The old name still compiles fine locally — it only breaks on a real Vercel build (ENOENT .../middleware.js.nft.json), so this is easy to ship and only discover in production. Always check node_modules/next/dist/docs/ for this project's actual installed version before assuming a Next.js convention.

△

Vercel blocks a deploy if the triggering commit's git author has no access to the linked GitHub repo — even without a formal GitHub "Login Connection" configured. Shows up as readyState: "BLOCKED" via the REST API (the CLI's own status output can be unreliable), with the message "the commit author doesn't have permission to create deployments for this project." Fix: correct the repo-local git config user.email to an identity Vercel/GitHub actually recognizes for the project, then push a new commit (an empty one is enough).

◇

Auth email confirmation differs by environment on purpose: local supabase/config.toml sets enable_confirmations = false for fast iteration, but the real hosted project defaults to mailer_autoconfirm: false (confirmation genuinely required) — check via the Supabase Management API before assuming local dev's laxer setting made it to production.
